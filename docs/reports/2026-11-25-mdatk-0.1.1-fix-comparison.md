# MDBridge's deliberate differences compared with MDATK's own fixes (0.0.4.1 → 0.1.1)

Read-only audit, 2026-11-25. Compared:
- MDBridge `docs/DIFFERENCES.md` (every entry) and `docs/IMPROVEMENTS.md` (all 124 register ids: the 121
  counted ones plus AN-25..AN-27);
- MDATK 0.1.1 (HEAD `1efa0ef`, the clone in the scratchpad), its CHANGELOG from 0.0.5 to 0.1.1, and
  `git diff v0.0.4.1 HEAD` of the code MDBridge has ported (`mdatk/analysis`, `spatial.py`, `selections.py`,
  `config.py`, `problems.py`, `pipeline.py`, `cli.py`, `projectfile.py`, `tomlio.py`, `io/`, `render/`,
  `citations.py`). The tags are squash commits, so a fix is dated by the release commit that holds it:
  `1710b51`/`02139e2` = 0.0.10, `6cb9fc6`/`19d4af6`/`b3505d9` = 0.0.13, `cd62c96` = 0.1.0, `1efa0ef` = 0.1.1.
  "file:line" below means MDATK HEAD unless it says MDBridge.

The main finding: since 0.0.4.1, almost all of MDATK's work went into the planner (RNAdo), the Amber, NAMD
and modelling steps, and ensembles. The code MDBridge ports changed in a small number of places
(about 80 lines in `io/` and `render/`, about 300 in `analysis/`), plus two larger new subsystems:
located problems with group-name suggestions (0.0.10), and the generic Lennard-Jones table (0.1.1).
MDATK still runs on MDAnalysis, so none of MDBridge's reader, selection-parser, periodic-geometry, RMSD or
rendering fixes have an MDATK counterpart.

Sections: §1 summary table, §2 detail of the C / D / M items (task step 3), §4 adopt candidates (task
step 4), §5 compatibility (task step 5); there is no §3.

Classes: **S** same or equivalent fix; **C** both fix it, details differ; **D** MDATK fixed it in a way
that conflicts (numbers, formats, semantics); **N** MDATK did not change it; **M** MDATK went further or
fixed a related issue that MDBridge did not.

## 2. Detail for the C, D and M items

### LD-05: a time step given vs the file's stored times (D)

- **MDBridge:** for files that store their own times (NetCDF with a time variable) the file's times are
  used, with `inputs.dt_ps (2.5 ps) differs from the time step in <file> (10.0 ps); the file's times are
  used` (src/io/trajectory.cpp:365).
- **MDATK 0.1.0** (CHANGELOG 0.1.0 "Time step override ... was ignored for trajectories with their own time
  stamps"): the override replaces the stored times. The time of analysed frame k is
  `frame_index × dt_ps` (analysis/base.py:283-286, pipeline.py:235-237, and a trajectory transformation
  `_FrameTimes` in io/loader.py:24-35, 70-71). The cache's input fingerprint gets
  `"time_axis": "frame x dt_ps"` when an override is set (pipeline.py:167-171), so older results are
  recomputed. The PDB export by time already used frame × override in 0.0.4.1.
- **Which makes more sense: MDATK's.**
  1. The setting is named and documented as an override: config.py:91, "Time between stored frames in ps
     (not set: from the trajectory's time stamps)". MDATK's GUI label is "Frames › Time step override"
     (problems.py `_LABELS`).
  2. Users set it when the stored times are wrong or useless. With a chain of NetCDF files, each file starts
     again at its own first time, so the stored axis is not monotonic. That breaks the time axes, the
     heatmap cell midpoints (RN-01) and external-data interpolation.
  3. With MDBridge's rule, export-by-time (frame × dt) and the time axis disagree for the same project.
- **Recommendation:** adopt MDATK's semantics. Keep MDBridge's warning, but reword it to what now happens:
  `inputs.dt_ps (2.5 ps) replaces the time step in <file> (10.0 ps)`. Add MDATK's `time_axis` fingerprint
  entry so that cache keys keep MDATK's meaning, and bump nothing else. Effort S–M (loader times,
  runner, pipeline frame axis, parity data for the `inputs.dt_ps` cases in loader_cases / pipeline_cases /
  cli_cases).

### AN-25: Lennard-Jones parameters without parm7, from residue templates (D)

- **MDATK 0.1.1** replaced the ad-hoc `GENERIC_LJ` table, but with a per-element typed table only
  (analysis/generic_lj.py:48-120; docs/GENERIC_LJ.md; energy version 2, energy.py:94). There is no residue
  template layer. Metadata keeps `lj_source = "generic"` and adds `lj_table` and `lj_default_elements`
  (energy.py:218-222).
- **MDBridge** matches residues against OpenMM's conversion of the Amber templates (ff14SB / OL15 / OL3 /
  TIP3P) first, and falls back to the typed layer (AN-26). Its metadata uses `lj_source` values
  `templates`, `typed` or `templates+typed`, plus `lj_atoms` and `lj_references`.
- **Conflicting numbers:** demo duplex, strand against strand, vdW in kcal/mol. MDATK 0.1.1 gives -34.1 (its
  changelog). MDBridge gives -34.62 from the templates and -34.74 from its typed layer alone. The parm7
  file's own parameters give -34.67. So MDBridge is within 0.05 kcal/mol of parm7 and MDATK within 0.6.
- **Which makes more sense:** MDBridge's on accuracy. Per-atom force-field types reproduce Amber, and the
  template layer also enables AN-27's charges. MDATK's on simplicity: a 30-row table with one rule per
  element, nothing that depends on residue position or chain-end heuristics, and easy to cite as a whole.
  The owner's rule favours the improvement, and MDBridge already treats MDATK's design as its fallback.
- **Recommendation:** keep MDBridge's. Merge the surface:
  - add MDATK's `lj_table` meta (a string naming MDBridge's table);
  - write a GENERIC_LJ.md-style record of MDBridge's two layers next to `data/sources/forcefields`;
  - keep `lj_source` values distinct, since nothing in MDATK reads them (checked: no consumer besides
    energy.py).

  Tell the owner that every non-parm7 energy will differ from 0.1.1. tests/parity/energy_parameters.py
  already models the difference test-side, so moving the reference to 0.1.1 only has to switch the patched
  baseline.

### AN-26: Amber atom types by element (C)

- **Same design:** parm10 `C N O P S F Cl Br I` for atoms of molecules; hydrogens by their bonded atom (`H`,
  `HO`, `HS`, `H1`; topology bond, else the nearest heavy atom of the residue within 1.45 Å); an atom alone
  in its residue that has a TIP3P ion set takes that ion (Joung–Cheatham, Li–Merz 12-6 CM, Mg²⁺ and Zn²⁺
  included); a metal inside a larger residue takes its ion's values; any other element takes carbon's, with
  a warning and `lj_default_elements`. The values are identical (generic_lj.py:48-90 against MDBridge's
  `amber_lj_types.tsv`).
- **Differences:**
  1. MDBridge refines by neighbours: `CT` for four-neighbour carbons (ε 0.1094 vs 0.086), `OS`, `OH`, and
     `OW` (TIP3P water O, 1.7683 / 0.152, against MDATK's carbonyl `O`, 1.6612 / 0.21).
  2. MDBridge gives extra points `EP` (0, 0). MDATK guesses an element for a TIP4P `EPW` or `M` site, finds
     no row and gives it carbon's parameters with a warning. That is wrong: a virtual site gets an LJ sphere.
  3. MDATK's hydrogen search always passes the frame's box (`ts.dimensions`, energy.py:167). MDBridge's
     follows `use_pbc`.
  4. Warning texts differ. MDATK: `energy: no generic Lennard-Jones parameters for element(s) X: carbon's are
     used (R* 1.908 Å, epsilon 0.086 kcal/mol)`. MDBridge: `energy: no Lennard-Jones parameters for
     element(s) 'X' (N atoms); carbon's (Amber type C) are used`.
- **Recommendation:** keep MDBridge's (the refinements and EP are corrections). Optionally take MDATK's
  wording that names the values. Effort: none, or S for the text.

### AN-04: triclinic minimum-image vectors (C)

- **MDATK 0.1.0** (spatial.py:52-67): for a cell whose angles are not `np.allclose` to 90°, vectors go
  through MDAnalysis' `minimize_vectors`. Pairs still come from `capped_distance`, so the AN-01 / AN-02
  issues remain. Cells within allclose of 90° still get the orthorhombic correction while their pairs used
  triclinic images, which is the AN-04 inconsistency at 90.0005°. The cache key marks it with
  `"use_pbc": 2` (analysis/base.py:217-218).
- **MDBridge:** one float64 image for pairs and vectors, an exact-90-after-float32 test, and version bumps.
- **Results** agree except at boundary pairs and nearly orthogonal cells.
- **Recommendation:** keep MDBridge's. If cache keys are to keep MDATK 0.1.1's meaning, encode `use_pbc` as
  MDATK does (`2` when on) — see CACHE-2.

### AN-10: N with a guessed hydrogen is no acceptor (M)

- **The item itself is S:** MDATK 0.1.0 does the same (hbonds.py:153-155).
- **Related fix MDBridge lacks:** in the distance-only mode (no hydrogens in the topology, or `use_angle`
  off), MDATK 0.1.0 counts each donor-acceptor atom pair once (hbonds.py:167-184). Before, two atoms that
  can both donate and accept, such as every N / O of a heavy-atom PDB or two hydroxyls, gave two bonds, one
  per direction. MDBridge still counts both directions (src/analysis/hbonds.py port,
  src/analysis/hbonds.cpp:190-225).
- **Recommendation: adopt.** It is a plain double count that inflates every distance-only H-bond series
  and map by up to 2×. Bump hbonds' version (see CACHE-2). Effort S.

### AN-23: contacts conventions, register KEEP (M)

MDATK 0.1.0 fixed three things in the contacts analysis (contacts.py version 2, lines 18, 33-38, 71-74,
86-89, 119-124) that MDBridge's register kept as conventions or did not see:
1. **A group against itself: per-residue counts.** The map holds each pair once (i < j), and
   `per_res_a` / `per_res_b` counted the pair on one residue only. A residue's count therefore depended on
   index order. Now both are row + column.
2. **Strand ends are no sequence neighbours.** `|ri - rj| <= 1` was excluded across chains too, so the last
   residue of strand 1 and the first of strand 2 (a duplex's closing base pair, consecutive residue
   indices) never counted. Now the exclusion applies only within one chain (`chain_ids`).
3. The `atom_pairs` series is labelled `atom contacts`, not `heavy-atom contacts`, when `heavy_only = false`.

All three are bugs, not conventions. **Adopt all three** (S). MDBridge's code is contacts.cpp:85-100
(neighbour rule), :174-182 (per-residue arrays and label). It needs a contacts version bump. Item 2 uses
`chain_ids`, so take §4 item 1 (chains from fragments) with it.

### RD-P06: format lines (M)

- **MDATK 0.1.0** fixed its own parm7 LJ-table reader (io/parm7.py:20-22, 69-74). It reads the format items
  `(a80)` (no repeat count; CHAMBER's CTITLE) and `(8(F9.5))` (ff19SB's CMAP parameters), and skips a format
  it cannot parse in a section nobody asked for (CHAMBER's `(i2,a78)`). Before, the energy analysis fell
  back to generic LJ for such topologies.
- **MDBridge's** topology reader skips unknown sections, so loading works. But its port of the LJ-table
  reader (`searchFormat`, src/io/parm7.cpp:79-120, and the throw at :962-970) still raises
  `cannot parse format line` before checking whether the section is wanted. For ff19SB and CHAMBER
  topologies, energy then warns and falls back to the non-parm7 parameters.
- **Recommendation: adopt** (S). Test with one CMAP and one CHAMBER header case.

### SEL-04, SEL-08 and CLI-07: selection error texts (C)

- **MDATK 0.0.10** (selections.py:203-243) keeps MDAnalysis' message but frames it:
  `invalid selection 'X' (expanded: 'Y'): MDAnalysis says: <message> (<hint>)`. The hints:
  - for the `'None'` token: `the selection ends where MDAnalysis expects more: a value, or a clause after
    and / or`;
  - for an unknown token: a case-insensitive or difflib (ratio ≥ 0.6) match against MDAnalysis' keyword
    list, `did you mean 'resname'?`;
  - for a token that is a group's name: `to use the residue group write group:Target`;
  - `Failed to find group: X` → `write group:X, with a colon ...`;
  - an unclosed parenthesis → `a parenthesis is not closed`.
- **MDBridge** replaces the parser messages themselves: `Unexpected end of selection after 'and'`, the
  lower-case keyword hint, and the `same` property list. Its outer text is still 0.0.4.1's
  `invalid selection 'X' -> 'Y': ...` (src/core/selections.cpp:375).
- **Which makes more sense:** MDBridge's parser messages are more precise. MDATK's typo and group-name hints
  and its "(expanded: …)" frame are better than MDBridge's 0.0.4.1 frame.
- **Recommendation: merge.** Keep MDBridge's messages. Adopt MDATK's frame without "MDAnalysis says"
  (MDBridge has no MDAnalysis): `invalid selection 'X' (expanded: 'Y'): <message> (<hint>)`. Add the
  difflib keyword suggestion and the group-name hints, generalising SEL-08's lower-case hint. Effort S.

### CIT-04: energy parameters cited by what was used (C)

- **MDATK 0.1.1** adds a project-level resource `generic_lj` = Cornell 1995, Wang 2000, Joung 2008, Li 2013
  (citations.py:93-96; generic_lj.py `CITATION_KEYS`). It is cited whenever the energy analysis is enabled
  and the topology is not a parm7 file used with `use_parm7`. That includes runs that meet no ion and no
  halogen, so Wang 2000 (parm99 Cl/Br) and Li 2013 can be cited without being used.
- **MDBridge** cites per run, by what was used (CIT-04 / CIT-06). It adds Jorgensen 1983 (TIP3P water
  template) and Li 2015 where used, and nothing at project level.

### CACHE-2: analysis versions and cache-key meaning (D)

- MDBridge numbered its versions as MDATK 0.0.4.1's + 1: energy 2, hbonds 2, rmsd 2, proximity 2, atoms 3,
  contacts 2, mg 2, basepairs 2, stacking 2, trace 5.
- MDATK 0.1.1 independently uses energy 2 (generic LJ), hbonds 2 (count once, N filter), contacts 2 (self
  group) and trace 5 (chains from bonds), and marks `use_pbc` as `2` in every key (base.py:218).
- So the same numbers mean different results. The caches are separate files (CACHE-1), so nothing is
  wrongly reused today. But MDBridge's claim that cache keys keep MDATK's meaning, and the "compare cache
  files by meaning" parity (cli_parity.py, tests/parity/analysis_versions.py), assume the 0.0.4.1 baseline.
- **Recommendation:** when the parity reference moves to 0.1.1, set each changed analysis to
  max(MDATK 0.1.1, MDBridge) + 1 (contacts 3, energy 3, hbonds 3, trace 6; the others to MDATK 0.1.1's
  value + 1). Adopt the `use_pbc: 2` encoding and the `time_axis` fingerprint (LD-05). Regenerate
  `analysis_versions.py`. Effort S, but it touches every cached-key expectation.

## 5. Project-file, cache and output-format changes since 0.0.4.1 that affect compatibility

**Project files (`.mdatk.toml`)**
- New workflow keys:
  - `workflow.supersede_runs` (true), `parallel` (default 0 at HEAD; a file without it reads as 1,
    config.py:1026-1027), `cpu_cores`, `gpus`, `last_node` (written only when set);
  - per step: `nodes[].adopted` and `nodes[].folder_tag` (written only when set) (config.py:454-458,
    487-495).

  MDBridge's loader warns `project: ignoring unknown key ...` (src/core/project.cpp:208) and **drops them
  on save**. Saving a 0.1.1 project in MDBridge therefore loses plan state (adopted runs, folder tags,
  budgets). Add these fields to MDBridge's model now, even unused (S). This is the most urgent
  compatibility item.
- New planner tools and step options (namd-mdff, user-script, structure builder, cluster job settings,
  DNA force fields, `rna_ff = "none"` …). Their `settings` tables are free-form and survive, but MDBridge's
  project-file comments come from 0.0.4.1's tool docs (`step_types.inc`), so comments for new options are
  missing. Also, MDATK changed `_tool_option` so that a repeated section's options are never documented as
  step options (projectfile.py:237-252).
- Step log: new `status` values `waiting` and `stopped`; new step `workflow supersede`
  (projectfile.py:66-71); the marker-inside-strings rule (§4 item 9). The lock file name is the same
  (`.<name>.lock`), and MDATK's is re-entrant now.
- validate() messages changed (config.py:694-973):
  - every problem starts with its location, e.g. `Analyses › Hydrogen bonds › Group A: unknown residue
    group 'X' (defined: …); did you mean 'Y'?`;
  - the uniqueness message is now `Residue group names must be unique: 'X' is also the name of group 1.`;
  - representation and structure-group unknowns are warnings unless the view is rendered;
  - selection syntax and circular definitions are reported.

  `info`'s JSON `problems` (cli.py:257) carries these strings. Scripts or tests that match MDBridge's
  current texts will differ. MDBridge's own additions (PRJ-01 texts, RN-15 field prefixes) should take the
  same `location: message` form when §4 item 12 is adopted.

**Cache and results**
- Cache-key meaning (CACHE-2):
  - `"use_pbc": 2` when on;
  - versions: energy 2, hbonds 2, contacts 2, trace 5 (same numbers as MDBridge's, other meanings);
  - inputs fingerprint `time_axis` when `dt_ps` is set;
  - the trace's selection texts are every group.

  The cache file format and manifest are unchanged (io/cache.py untouched). MDBridge never reads MDATK's
  caches, so there is no data hazard, only key-parity work.
- New result fields:
  - trace array `backbone` (bool per row);
  - energy meta `lj_table` and `lj_default_elements` (MDBridge has the latter, not the former);
  - contacts series label `atom contacts` when hydrogens count;
  - external-data keys with `-2`, `-3` … for repeated names (affects panel and chart keys that users write).
- Analysis errors and logs: errors raised while analysing are prefixed with their setting's location.
  `analyze` / `render` print `WARNING: <location>: ...` for warning-level problems before running.

**Citations / params log**
- New resource `generic_lj` (keys cornell1995, wang2000, joung2008, li2013).
- About 219 lines of new citation entries (DNA OL15 / OL21 / OL24, NAMD, MDFF, …) in
  `_citation_data.py`. MDBridge's `citation_data.inc` is generated from 0.0.4.1's table. Regenerate from
  0.1.1 (through `improvements_citations.py`) so that keys in 0.1.1 params logs resolve; today
  `withRunKeys` silently drops unknown keys.

**User settings**
- `~/.config/mdatk/settings.toml` (shared by both programs) now also holds `cat_proof`. MDBridge's
  `addRecent` deletes it (§4 item 11).
